## 0. 目的とスコープ

| 項目 | 内容 |
|---|---|
| 目的 | 緊急時に動く閉伊川水門の動きを、止まっている実物の前でARを使って伝える |
| 対象施設 | 閉伊川水門のみ |
| 作るもの | ①現地AR（実物大で実物に重ねる） ②床置きAR（床や机の平面を検知して縮小モデルを置く） ③3Dビューア（非対応端末向けの代替） |
| 作らないもの | AR上での水理シミュレーション（水位は見た目の面だけ） |
| 主な利用者 | 現地の見学者、市の説明・展示。学校の防災授業で使われる可能性もある |
| 検証の場所 | 自宅・大学（岩手県立大学 第二地域連携棟）。現地での最終検証は11月の予定 |
| 実機 | 手元のiPhoneのみ（協力が得られればゼミのメンバーの端末も使う） |

## 1. 決定事項

| 区分 | 決定 |
|---|---|
| 現地AR | 10方式（§4.3）を検証して1つ採用する。GPSで大まかに置き、マーカーなどで精度を上げ、実世界に固定して見せる |
| 現地ARの絶対原則 | **カメラに張り付く・カメラの動きだけに追従するように見える挙動は禁止** |
| 現地ARの視点 | どこからでも見られるようにする。カメラの位置を推定して、実際の位置関係で表示する |
| 床置きAR | 平面を検知して置く。既存のマーカー版（`/ar/marker`）は置き換える |
| 床置きARの技術 | OSSを優先する。AlvaAR → 擬似配置 → Quick Look の順に下げる |
| 床置きARのサイズ | 全幅1mで置く。ピンチで0.1m〜実寸まで変えられる |
| 端末ごとの処理分岐 | 原則しない。どうしても必要な場合だけ分ける |
| 公開版 | 開発者向けの跡（比較ページ・デバッグUI・テスト用の地点）を残さない。ユーザー第一の設計 |
| 言語 | 日本語と英語。既定は日本語 |
| 計測 | 仕込んでおくが、既定はOFF |
| 音声 | 音声合成で作る。後回しでよい |
| 開発の流れ | 機能ごとに開発ブランチを切り、PRでmainに入れる |
| ライセンス | **保留**（§10.3のゲートを参照） |

## 2. 用語

| 用語 | 意味 |
|---|---|
| 現地AR | 水門の実物の前で、実物大のモデルを実物に重ねて表示するAR |
| 床置きAR | 床や机の平面に縮小モデルを置いて、回したり拡大縮小したりするAR |

| 方式 | 現地ARの位置合わせと固定のやり方（A〜J） |
| 検証用の地点 | 第二地域連携棟。現地ARの精度を事前に確かめるために使う |

## 4. 現地AR

### 4.1 要件

| # | 要件 |
|---|---|
| O1 | モデルは実世界に固定されて見える。カメラに張り付く挙動は禁止 |
| O2 | どこから見ても、実物との位置関係が正しい |
| O3 | 位置・大きさ・向きの基準値は地点の設定ファイル（JSON）だけで持つ（既存の原則を維持） |
| O4 | 扉の開閉アニメを、動画のように再生・一時停止・シークできる |
| O5 | GPSは粘って表示を試みる。どうしてもだめならエラーを表示する |
| O6 | 権限を拒否されたら、そのたびに確認画面を出す |
| O7 | 非対応端末では「この端末では表示できません」を出し、3Dビューアに案内する |

### 4.2 張り付きの評価指標

| 指標 | 測り方 | 合格の目安 |
|---|---|---|
| 位置のずれ | 30m離れた地点で、建物の角とモデルの角のずれ | 対象の幅の5%以内 |
| 静止中のドリフト | 60秒動かさずに持ったときのずれの変化 | 目で見て分からない程度 |
| 歩いた後のずれ | 20m歩いて戻ったときのずれ | 対象の幅の5%以内 |
| カメラ追従 | 端末を回す・歩くときに、モデルが一緒に動いて見えないか | 一度も起きない |
| 起動時間 | 開始のタップから表示まで | 10秒以内（Wi-Fi） |
| 成功率 | 5回試して表示まで行けた回数 | 5回中4回以上 |

### 4.3 検証する方式

| # | 方式 | 位置の決め方 | 固定の仕組み | 使うOSS | 優先度 |
|---|---|---|---|---|---|
| A | LocAR.js（既存） | GPS＋コンパス | 向きだけ追跡 | locar | 比べる基準 |
| B | AR.js位置情報版（既存） | GPS＋コンパス | 向きだけ追跡 | AR.js | 比べる基準 |
| C | DeviceOrientation（既存） | GPS＋コンパス | 向きだけ追跡 | 自作 | 比べる基準 |
| D | シルエット手合わせ＋SLAM | GPSで仮置き → シルエットを手で合わせる | SLAM | AlvaAR | 高 |
| E | 印刷マーカー | 位置の分かった場所に貼ったマーカーで、位置・向き・実際の大きさを決める | SLAMで維持 | js-aruco2 ／ AprilTag | 高 |
| F | 画像ターゲット | 看板や銘板の写真を目印にする | 写っている間＋SLAM | MindAR | 中 |
| G | 2点照準合わせ | 画面中央の十字を対象の左右の端に順に合わせてタップし、向きと位置を決める | SLAM | 自作 | 高 |
| H | GPS・コンパス・SLAMの自動融合 | カルマンフィルタで自動補正する（手合わせなし） | SLAM＋GPS | 自作 | 中 |
| I | 輪郭の自動合わせ | 3Dモデルの輪郭を映像のエッジに自動で合わせる | 自動追跡 | OpenCV.js | 余力があれば |
| J | 自作のVPS | 事前に写真から点群の地図を作り、端末の画像と照合して位置を出す | 位置を推定し直す | COLMAP＋OpenCV.js | 余力があれば |

- 検証の順番: A〜C → D・E・G → H・F → I・J
- Niantic VPSは非OSSなので候補外。D〜Hでどうしても操作感が解決しない場合だけ候補に戻す
- カメラ1台のSLAMでは実際の大きさ（スケール）が分からない。D・G・Hでは、位置合わせの段階でスケールを決める方法も一緒に検証する（Eはマーカーの実寸で決まる）

### 4.4 採用の決め方

1. 第二地域連携棟で全方式を§4.2の指標で測り、`docs/eval/` に記録する
2. 上位2〜3方式を11月の現地訪問で比べる
3. 採用した方式と、採用しなかった方式の理由を `docs/eval/decision.md` に書く
4. 採用した方式を `/ar/onsite` に組み込む

## 5. 床置きAR

実装メモ（2026-10-10）: `/ar/place` にWebXR Hit TestとQuick Lookによる机・床への配置を追加した。ユーザー指定の手のひらサイズに合わせ既定全幅は20cm。以下は従来の計画であり、実装済み範囲・採用理由・仕様との差異は [plane-ar.md](plane-ar.md) を参照する。AlvaARは未導入。

### 5.1 技術の順番

| 順 | 方式 | 平面の検知 | 条件 |
|---|---|---|---|
| 1 | AlvaAR（GPLv3、SLAM） | する | 技術検証（§11のP1）に合格したら本線にする |
| 2 | 擬似配置（ジャイロ＋床の高さを仮定） | しない | 1が不合格の場合 |
| 3 | Quick Look（USDZ） | する（OSの機能） | 1と2がどちらも使えない場合。独自UIは使えず、扉のアニメ再生だけになる |
| 予備 | 8th Wallのエンジンバイナリ | する | 非OSS。上の3つがすべてだめな場合だけ検討する |

### 5.2 機能

| # | 機能 | 内容 |
|---|---|---|
| P1 | 置く | 平面を検知したら照準を出し、タップで置く |
| P2 | 置き直し | ボタンで置き直す |
| P3 | 回転 | 2本指で回す |
| P4 | 拡大縮小 | ピンチで0.1m〜実寸。既定は全幅1m |
| P5 | 扉の開閉 | 5つのアニメクリップを同時に再生。再生・一時停止・シークができる |
| P6 | 水位スライダー | 見た目だけの水面を上下させる（シミュレーションはしない）。範囲の値は後で決める |
| P7 | 断面 | 切断面をスライダーで動かす（Three.jsのクリッピング） |
| P8 | 解説の注釈 | モデル上のアイコンをタップすると解説がポップアップする |
| P9 | UIの最小化 | 操作パネルを畳んで、画面にほぼ何も出さない状態にできる |

- カメラに張り付く挙動を禁止する原則は、床置きARには当てはめない（現地AR専用）。ただし平面を検知できている間は、置いた位置に固定されることを目指す

## 6. 共通のUI/UX

| 項目 | 方針 |
|---|---|
| 流れ | 説明 → 権限の許可 → 配置（位置合わせ） → 体験 → 終了 |

## 7. 3Dモデル

| 項目 | 方針 |
|---|---|
| 元ファイル | `public/models/suimon-kousin.glb`（24.6MiB、約39万三角形、アニメ5クリップ） |
| 圧縮 | MeshoptとDracoの両方を試し、扱いやすい方を採る。試算ではMeshoptが4.24MiB、Dracoが1.72MiB |
| 比べる観点 | iPhoneでの読み込み時間、見た目の崩れ、デコーダの同梱しやすさ |
| 目標サイズ | 5MiB以下 |
| 三角形の削減 | 自動の簡略化ではほとんど減らない（35万が限界）。動作が重い場合だけBlenderで手作業で減らす |
| 現地用と床置き用 | 原則は1ファイルで兼用する。重すぎて支障が出る場合だけ分ける |
| 実寸 | 図面はない。おおよその大きさを後で確かめ、設定ファイルに入れる |

## 8. 非機能要件

| 区分 | 要件 |
|---|---|
| 性能 | 起動から表示まで10秒以内（Wi-Fi）、描画30fps以上（目標値として置く） |
| 対応端末 | セキュリティ更新が続いていて、利用者の割合が高いiOSとAndroidの版を対象にする。具体的な版は技術検証で決める |
| 外部ライブラリ | 通信が不安定でも動くように、原則は同梱する。ただしページの読み込みが極端に遅くなるものは除く。raw.githackからの読み込みはやめる |
| ライブラリの併用 | 競合しない限り認める。Three.jsが二重に読み込まれないように注意する |
| 計測 | Cookieを使わない方式を仕込む。既定はOFF。ONにする手順をREADMEに書く |

### 8.1 セキュリティ

| # | 要件 |
|---|---|
| S1 | 秘密情報（APIキー・トークン）をリポジトリやビルドに入れない |

## 10. 開発の進め方

### 10.1 ブランチ

| 種類 | 名前の例 | 中身 |
|---|---|---|
| 技術検証 | `spike/<名前>` | 試すだけ。mainには入れない |
| 機能 | `feat/<名前>` | 1機能1ブランチ。PRでmainに入れる |
| 修正 | `fix/<名前>` | バグの修正 |

### 10.2 PRの条件

- `npm run check`・`npm run test`・`npm run validate-config`・2種類のビルドがすべて通っている
- iPhoneで確かめた結果（スクリーンショットか記録）を添える
- 新しく入れたライブラリのライセンスと `npm audit` の結果を書く

### 10.3 ライセンスのゲート

- ARv2のライセンスは保留中である
- **GPLv3のライブラリ（AlvaARなど）を含むコードは、ライセンスが決まるまでmainに入れない。pushもしない**（ローカルの `spike/` ブランチだけで扱う）
- MIT・BSDなど、制限の緩いライセンスのライブラリは通常どおり使ってよい
