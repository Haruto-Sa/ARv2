# 通常ビューアの描画負荷と E2E

## 調査の範囲と判断

対象は [CI run 38382470138](https://github.com/Haruto-Sa/ARv2/actions/runs/38382470138/job/115246025172) の `3035e5d`。型・単体・ビルドは成功し、E2E は 21 件中 16 成功、3 失敗、2 再試行成功だった。ボタンの actionability 確認後もクリックが完了せず、30–60 秒でタイムアウトしている。元の CI は成果物をアップロードしておらず、当時の trace を取得できない。`session closed` はタイムアウト後の終了でも発生するため、ブラウザクラッシュの証拠として扱わない。

失敗コミットと、その後の `dd808a8`（通常表示の30fps制限・不要描画スキップ）を区別する。今回の変更は後者に積み重ねる。ガイドのフォーカス処理に無限ループは見つかっていない。ローカルでは失敗コミットでも元の重い10ケースを各3回、1/2ワーカーで全て成功したため、CIの直接原因は未確定。

確認できた負荷要因は、停止中・ガイド表示中にも描画する旧ループと、並列時の個別テストの長時間化。モデルは25,835,712 bytes、9 primitives、392,488 triangles、5 animations。モデル準備より操作待ちの時間が大きく、まず不要な描画を減らす。モデル削減・一律の解像度低下は今回行わない。

## 描画とライフサイクル

- 通常ビューアは変更時にフレームを予約し、再生・OrbitControls の減衰中だけ継続する。停止中もサイズ・向き・視点・ウィンドウサイズ変更で再描画する。30fps上限は既存修正を継承。
- 減衰は経過時間に応じて更新する。固定のフレーム当たり減衰では、低fps時に回転が長く残ることを実モデルテストで確認した。
- 非表示タブ、カメラ起動前、使い方・検証モーダルでは通常ビューアの RAF 自体を止める。モーダル背景には直前の静止画を残し、閉じたら再生を再開する。隠れていた時間をアニメーションに加算しない。
- BFCache の pagehide は一時停止、pageshow は再開。通常の離脱は RAF、DOMリスナー、Observer、Controls、ミキサー、モデルの geometry/material/texture/ImageBitmap を解放する。遅れて読み込みが終わったモデルも解放する。
- XR は renderer のセッション用ループで更新する。通常ビューアの停止条件や30fps制限を適用せず、hit-test、トラッキング、アンカー、配置更新を維持する。セッション終了後は通常表示に戻る。

Three r175の実装も確認した。XR開始後に `renderer.setAnimationLoop` を呼ぶとwindow側RAFも開始するため、XRManagerだけにコールバックを設定する。またrendererは `sessionend` でwindow側RAFを再開するので、その内部リスナーの後で明示停止する。XRFrameのない呼び出しではXR描画しない。この経路の実セッション動作は下記の実機確認対象。

## 再計測

### 測定結果

macOS / Node 22.23.3 / 同一Playwright Chromium。元の10ケース×3回、実モデル、再試行なし。所要時間はビルド・サーバ起動を含むPlaywright集計値。

| 実行条件 | 失敗コミット3035e5d | 修正後（dd808a8 + 本PR） |
| --- | --- | --- |
| 1ワーカー | 30/30成功・298.5秒 | 30/30成功・96.3秒 |
| 2ワーカー | 30/30成功・242.4秒 | 30/30成功・69.0秒 |

失敗率はいずれも0/30であり、CI失敗の再現・根絶を証明する数値ではない。元の検証ダイアログのケースは1ワーカー24.4秒、2ワーカー41.0秒（各3回中央値）。並列化で総時間は短縮しても、個々のタイムアウト余裕が減る。重いプロジェクトだけ1ワーカーにする理由はこの観測にある。[ケース別測定値](measurements/viewer-e2e.json)。

通常CPU、390×844、DPR1、各3回中央値。停止・ガイドは約2秒の観測窓。

| 指標 | 3035e5d | 既存修正dd808a8 | 本PR |
| --- | ---: | ---: | ---: |
| 扉停止中のRAF回数 / draw回数 | 11 / 99 | 120 / 0 | 0 / 0 |
| ガイド表示中のRAF回数 / draw回数 | 6 / 54 | 120 / 0 | 0 / 0 |
| モデル準備 ms | 1088 | 612 | 629 |
| 停止クリック完了 ms | 2275 | 1221 | 1266 |

大きな改善は既存修正にも由来する。本PR固有の効果は、アイドルRAFの除去、低fpsでの減衰時間の補正、ライフサイクル管理とテスト分離。全操作が既存修正より高速になったわけではなく、再描画タイミングによるばらつきもある。再生中は依然として重く、約2秒窓で約2秒分のlongtaskが観測される。これはモデル・描画パイプラインの負荷が残ることを示し、低性能実機での性能保証にはしない。

CPU4倍制限でも停止中/ガイド中はRAF・drawとも0。最終版のクリック完了中央値は停止1360ms、サイズ/向き33ms、ガイド開始320ms、閉じる299ms、再生29ms。新規実WebGLテストもCPU1倍/4倍で成功。クラッシュイベントは計測した全18回で観測なし。[描画・longtask・操作時間の全測定値](measurements/viewer-render.json)。実ブラウザのGPU完了時間は計測していない。

Node 22、同じChromium、他のブラウザ検証を並行実行しない条件で測定する。

```sh
# 比較対象の元の e2e を別 worktree に保持。1/2 をそれぞれ3回。
CI=true COMPARISON_TEST_DIR=/path/to/baseline/e2e \
  npx playwright test -c scripts/performance/compare.config.ts \
  --workers=1 --repeat-each=3 --retries=0 --reporter=list,json

# 同じ静的プレビューに対するローカル計測。CPU_RATE=4 でも繰り返す。
VIEWER_URL=http://127.0.0.1:4324/viewer CPU_RATE=1 \
  MEASUREMENT_OUTPUT=/tmp/viewer.json node scripts/performance/measure-viewer.mjs
```

計測スクリプトの2秒窓とテストの静止観測窓は、負荷/停止を観測するためのもの。クリック前の固定sleepで成功させる処理ではない。draw呼び出し時間はGPU完了時間ではなく、longtaskにもGPU待機等を含み得る。CPU4倍制限は低性能端末のGPU・発熱・メモリの再現ではない。

## PR上のLinux検証で分かったこと

初回の追加テストは設定→ドラッグ→モーダル→ページ復帰を1ケースにまとめており、[run 38434164972](https://github.com/Haruto-Sa/ARv2/actions/runs/38434164972)では既存21件成功、追加2件が30秒のケース上限に到達した。保存できた初回traceでは停止クリック6.6〜8.7秒、5ステップのドラッグ14.5〜15.5秒。クラッシュイベントは両方false。失敗時の単独スクリーンショットは取得されなかったが、traceの画面列は残り、実モデル表示と操作途中の状態を確認できた。

GPU ReadPixels待ちの警告もあったため、連続画面キャプチャを外した対照実行 [38435161586](https://github.com/Haruto-Sa/ARv2/actions/runs/38435161586)を行った。しかし停止6.5〜8.5秒、ドラッグ14.4〜15.5秒でほぼ変わらず、キャプチャだけを原因とする仮説は支持されなかった。診断情報を維持するため設定は戻した。

コード確認で、10fps未満ではアニメーションのdelta上限0.1秒がカメラ減衰にも適用される問題を修正。カメラは実経過時間、アニメーションだけ上限付きとし、長い描画フレームでも減衰が長引かないようにした。加えて、設定・再生・カメラ・ライフサイクルを独立ケースにし、各操作の失敗箇所と時間を分けて確認する。タイムアウト・再試行の上限は変更しない。

[減衰修正後のLinux CI](https://github.com/Haruto-Sa/ARv2/actions/runs/38439407738)は型・単体72件・両ビルド・E2E27件すべて成功（E2E 2.2分）。CPU4倍の設定ケースが26.8秒だったため、再生確認を独立させ、29件構成で余裕を増やす。比較測定値は最終の製品コード `a7fe6fc` で取り直した。

## 残る実機検証

1. Android WebXR: 起動、平面検出、配置、歩き回った際の固定、追跡喪失/回復、リセット、アンカー有無、終了/再開始。ガイドと検証モーダル中もトラッキングが維持され、UIタップで誤配置しないこと。
2. iPhone Safari: Quick Look起動、実空間のサイズ/向き、閉じる/再起動。ヘッドレスのUSDZ生成成功だけでネイティブ配置精度は保証しない。
3. 低性能端末: 扉停止後の回転/ピンチ、サイズ/向き、縦横回転、タブ切替、履歴戻る（実BFCache）、ガイド開閉。背景が静止し復帰後に飛ばないこと。
4. 数回の離脱/再入場でGPUメモリ・リスナー・ループが増え続けないこと。XR中のOSバックグラウンド化/復帰と権限拒否も確認する。
