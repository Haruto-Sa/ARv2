01 / Purpose & Outcome

水門を、
机の上の実空間へ。

閉伊川水門の既存GLBを再利用し、スマホでは平面AR、PCでは扉の動きと形状を確認できる3Dビューアへ進む。

20 cm

配置時の既定全幅。高さではなく、向き補正後の幅から倍率を求める。

2 routes

WebXRによるWeb内ARと、USDZを使うOSのQuick Look。

Static

Astroの静的配信。AR計算・変換・描画はブラウザと端末側で行う。

ユーザーによるスマホ動作確認済み。 このチャットで報告を受領。ただし機種・OS・利用したAR経路・精度の定量値は未記録。全端末での動作を保証する結果ではない。

05 / Entry Flow

カメラはユーザーの操作から起動する

① 対応スマホ

タッチ対応 + coarseポインターを確認し、isSessionSupported('immersive-ar') または relList.supports('ar') が使えるかを確認する。

モデルを準備する間は3D確認画面を隠す。準備後の「カメラを起動」1タップで次へ。

② PC・非対応スマホ

location.replace(withBase('/viewer'))で形状・動きの確認画面へ。カメラの許可要求はしない。

スマホの起動画面からも「3Dビューアで見る」を選べる。

カメラ利用の説明
→
起動タップ
→
OS・ブラウザの許可
→
カメラ / 平面探索 / 配置
ここでいう確認はカメラ・ARの権限。ログイン認証ではない。許可済みならOSは確認を省略することがある。Quick LookのAR/Object初期タブもOS側で管理される。

タッチ対応PCなどではスマホ判定が一致しない可能性がある。WebXRのセッションにはHit Test・local・DOM Overlayも必要なため、AR可否の事前確認だけで起動成功を保証しない。

06 / WebXR Hit Test

作るのは床のメッシュではなく、配置する交点

端末のAR基盤が検出した平面に、視点からのレイを当てる。アプリは得られた位置と向きに円の照準を描く。平面ポリゴンを取得して独自に床メッシュを生成する実装ではない。W3C Hit Test仕様

requestSession('immersive-ar', {
  requiredFeatures: ['hit-test', 'local', 'dom-overlay'],
  optionalFeatures: ['anchors'],
  domOverlay: { root: overlay }
});
const viewer = await session.requestReferenceSpace('viewer');
const source = await session.requestHitTestSource({
  space: viewer, entityTypes: ['plane']
});

配置前: 毎フレーム照準を更新

frame.getHitTestResults(source)から水平面の結果を選ぶ。位置が取れなければ円と配置ボタンを無効にする。壁・天井は候補から除く。

タップ時: 座標をコピー

次の有効なXRフレームで配置を確定する。モデルを照準の子やカメラの子にしない。配置後のカメラ移動は視点だけを変える。

Android ChromeのWebXR ARはARCoreを使用するという説明がある。実装はこの基盤をブラウザAPI越しに利用し、独自SLAMは書いていない。Google公式説明

07 / Geometry Lab

位置とサイズの意味を、コードで揃える

底面中央を原点へ

設定のyawを適用してBox3で計測。水平中心をX/Z原点へ、底面をY=0へ移す。中央原点のまま置くと水門の下半分が机に埋まる。

scale = 0.2 / measuredWidth

GPS用の高さ5mから縮尺を決めない。今回の机上模型は幅20cmが基準。

上向きの水平面を選ぶ

Hit Test姿勢のY軸を法線として扱い、matrix[5] ≥ 0.9を採用条件にする。理想的な単位法線では上向きから約25.8°以内に相当する。

この判定は傾きのフィルター。平面の広さ・信頼度・机か床かの分類はしていない。

0° / ny = 1.000 / 採用

設定: public/config/placement.json — 既定0.2m、最小0.1m、最大1m、しきい値0.9。

08 / Tracking & Lifecycle

置いた後の「固定」は、2段階で扱う

Anchorが使える場合

有効フレーム内で hit.createAnchor() を呼ぶ。以降はAnchorのposeを取得し、端末の追跡補正を反映する。視点またはAnchorのposeが失われたらモデルを隠す。

未対応・作成失敗の場合

local参照空間で決めた位置・向きを維持する。Viewer poseが失われたら隠す。アンカーを使う場合と同じ精度を保証するものではない。

探索 → 照準あり → 配置待ち → 配置確定 → 追跡
 ↑                                      │
 └──────────── 置き直し ──────────────────┘

置き直し / 終了: generation++ → anchor.delete()
遅延して届いたAnchor: 世代番号が違えば削除
終了: hitSource.cancel() → XR終了 → 画面を復元
ページ離脱: loop停止、geometry/material/texture解放、Blob URL解放
Anchor作成は非同期。「置き直す」を押した後に古いPromiseが完了しても、前の位置へ戻らないよう世代番号で無効化している。

座標は永続保存しない。ページ再読み込みや次のARセッションに配置位置を引き継ぐ機能はない。ドリフト・再局在化の挙動は端末で確認する。

09 / Native AR Asset Pipeline

同じ水門をQuick Lookで表示するための補正

Three.jsの USDZExporter を使い、メッシュとマテリアルを静止USDZへ変換する。BlobのMIMEは model/vnd.usdz+zip、生成したURLを <a rel="ar"> に渡す。変換のためにモデルを外部サービスへ送らない。

GLB / Three.js scene
→
行列を頂点へ焼き込む
→
反転・両面の補正
→
USDZ / Blob / Quick Look

負のスケール

元GLBの複数ノードに [-1,-1,-1] がある。出力用ジオメトリへworld行列を適用し、行列式が負なら三角形の頂点順を交換する。元のGLB・Web表示用のジオメトリは変えない。

両面マテリアル

同梱ExporterはDoubleSideを表現しない。裏向きの三角形と逆向き法線を追加し、FrontSideマテリアルで両面を表現する。見え方を維持する代わりに出力三角形が増える。

この変換は静止モデル。扉のアニメーションはUSDZに含めない。Quick Look自体はアニメーションを扱えるが、今回のExporter経路では輸出していない。Webの3DビューアではGLB内のクリップを再生する。

制限: 現モデルのMeshStandardMaterialを対象にする。複数マテリアル配列はエラーにする。任意のスキニング・モーフ・シェーダーの再現を保証する汎用変換ではない。画像上限1024、変換時CPU/メモリと出力容量が性能上の確認点。

10 / UI Ownership

カメラ画面の所有者で、できることが変わる

項目WebXR今回のQuick Look経路3Dビューア
描画・配置WebGL + XRのposeOSのAR画面WebGL、実空間追跡なし
扉の動きAnimationMixerで複数クリップ再生静止USDZのため再生しない再生 / 一時停止
回転・サイズWebのスライダーOSの操作スライダー + OrbitControls
左上ホームDOM Overlayに表示。XRを終了して移動OSの×を閉じた起動元ページに表示通常のWebリンク
権限・初期画面ブラウザが権限を管理OSが権限とAR/Object選択を管理カメラは要求しない

Quick Lookの「×」はWebページのDOMではない。公開されたバナー/カスタムアクションはあるが、標準の左上ボタンを置き換えるAPIは確認できないため、今回は置き換えない。Appleのカスタムアクション資料

よく聞かれる質問への答え

「なぜiPhoneのARには扉再生ボタンがない？」— OSのQuick Lookへ表示を渡しているため。今回の静止USDZと標準UIではWeb側のAnimationMixerやDOMボタンはその画面へ持ち込めない。独自UI付きの同等体験を目指すなら、別のWebAR基盤またはネイティブアプリとして設計し直す必要がある。

11 / Alternatives

「AR」という名前でも、観測できる情報は違う

方式手がかり・得られる情報今回採用しない理由 / 使いどころ
LocAR / GPS緯度経度、精度、方位、高度。近距離で東・北のメートルへ変換現地の大まかな位置向け。机の接地面を検出する仕組みではない
独自DeviceOrientation端末の向き、画面方向、別途GPS回転だけではカメラの並進が分からない。位置固定の品質は別途検証
AR.js + A-Frame宣言的な3Dシーンと既存位置情報AR既存比較用。今回の平面ARのAPIやUSDZ出力はThree.jsへ直接接続
AR.js Hiroマーカー印刷パターンから相対姿勢目印が必要。印刷なしの机・床配置とは要件が違う
AlvaARブラウザ内の単眼SLAM / world tracking実寸・平面の検証とGPLの扱いが未確定。リポジトリのライセンス方針により未導入
擬似配置方位センサーと仮定した床高実平面を観測しない。実検出として見せる方式に今回はしない
ネイティブARKit / ARCoreOSの追跡・平面機能をアプリから利用独自UIを作れる候補だが、今回の静的Webの範囲では新規アプリを作らない

SLAMは自己位置と環境を推定する考え方。GPSやジャイロを読んだだけでSLAM相当になるわけではない。単眼SLAMの採用では、実寸スケールと追跡喪失時の挙動も評価する。AlvaAR一次資料

12 / Existing Systems

水門AR以外の部品も、混同せず説明する

地図と地点設定

Leafletが地点カタログからピンを表示する。地図タイルは外部サービス。位置情報ARは地点JSONの座標・yaw・高度・高さを使う。平面ARはモデルパスとyawを再利用し、置く位置はHit Testで決める。

GLBと圧縮

GLBには形状・マテリアル・画像・5つのアニメクリップがある。Draco/Meshopt版とデコーダは比較用に存在するが、今回の共通ローダーは設定された非圧縮GLBを使用する。

Unity WebGL

public/unityのビルド成果物を独立したページとして配信。Three.js平面ARとはレンダラー・データ形式・操作ループが異なる。今回Unityのシーン・C#・AR Foundationは変更していない。

ヒーローのWebGL水面

トップページの水の表現は src/lib/water-shader.ts。装飾の描画であり、ARの平面検出や水理シミュレーションではない。

本番では比較用の/lab、AR.js/A-Frameのvendor、検証地点JSONを出力後に除外する。開発・比較時はINCLUDE_LAB=1。この整理は今回のPRが依存する既存ブランチの変更。

13 / Delivery

静的配信とHTTPSで、スマホまでつなぐ

配信パス

Cloudflare Pagesはルート、GitHub Pagesは/ARv2/。withBase()でモデル・設定・遷移先をビルド時のBASE_URLに合わせる。ハードコードしたルート相対URLはサブパスで壊れる。

HTTPS検証

PCのAstro devをCloudflare Tunnel経由で公開する。スマホのカメラ・ARには安全なコンテキストが必要。サーバーのHost制限は接続ヘッダーで解決する。

npm run dev -- --host 127.0.0.1 --port 4326
cloudflared tunnel --url http://127.0.0.1:4326 \
  --http-host-header localhost

# 発行されたHTTPS URL + /ar/place をスマホで開く
# PCとトンネルは検証中、起動したままにする

CIはNode 22で型チェック、単体テスト、設定検証、両配信先向けビルド、lab除外チェック、Playwrightを実行する。アプリ用のAPIサーバーやデータベースはない。権限と端末機能はブラウザ・OSで管理する。

この資料は外部JS・フォント・CDNを読み込まない単一HTML。ブラウザでローカルファイルとして開ける。参照リンクを開く場合だけネットワークを使う。

14 / Evidence & Limits

確認できたことと、まだ測っていないこと

確認済み

  • ユーザーがスマホで動作を確認し、本チャットで報告
  • 単体テスト62件: 水平面、接地、幅、反転・両面補正、設定・既存計算
  • 関連ブラウザテスト5件: PC遷移、スマホUSDZ準備、拒否後の再試行、非対応遷移、ビューア
  • 型チェックと静的ビルド。既存の非推奨設定警告あり

確認を広げる項目

  • 機種、OS、ブラウザ、WebXR/Quick Look経路を記録
  • 60秒のドリフト、周囲からの視差、暗所・無地の机
  • Anchor対応/未対応、喪失・復帰、終了・再開
  • USDZ変換時間・最大メモリ・外観と初期20cm幅
既存トップページの自動スクロールE2Eは、以前のローカル実行で失敗した履歴がある。今回の関連5件の通過を、全E2Eの通過と読み替えない。実機報告も全端末・定量精度の評価とは分ける。

今後の拡張: 圧縮モデル経路の評価、USDZの事前生成、ARのピンチ・2本指回転、扉シーク、水位の見た目、断面、注釈、英語UI。現時点の対応は幅0.1〜1mのスライダーと扉の再生/一時停止。
